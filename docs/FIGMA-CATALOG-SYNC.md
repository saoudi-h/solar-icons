# Figma catalog synchronization

The Figma plugin is an offline application. Its UI embeds the catalogue generated by
`@solar-icons/static`; it does not fetch new icons at runtime. This makes the generated plugin
artifact the boundary between the package release and the Figma Community listing.

## Synchronization contract

`packages/figma-plugin/scripts/build.mjs` embeds three catalogue payloads in `dist/ui.html`:

- the complete `icons.json` SVG map;
- `metadata-descriptions.json`, whose length is the logical icon count;
- a provenance object containing the static package version, logical icon count, six-style count,
  canonical SVG count, alias SVG count, total map entries, and a deterministic SHA-256 catalogue
  hash.

The hash covers the semantic contents of the SVG map and metadata, not JSON whitespace or object
key order. The package version is tracked separately, so a version-only change remains visible
without pretending that the icon data changed.

## Automated work

Run this from the repository root:

```sh
pnpm check:figma-catalog
```

The command:

1. rebuilds `@solar-icons/static` from the core source of truth;
2. rebuilds the Figma plugin and embeds the current static output;
3. compares the embedded SVG map and metadata with the static package;
4. verifies the embedded provenance, including the deterministic catalogue hash; and
5. fails if a build placeholder or stale catalogue remains in `dist/ui.html`.

The release and beta-release workflows run the same check. `dist/` is generated and ignored, so
the check must run after every catalogue or plugin build rather than relying on a committed bundle.

## Manual work that remains

Figma Community publication cannot be completed by the repository build. It requires a maintainer
to use Figma Desktop, select the plugin manifest, review the listing, and submit the new version to
Figma's publication/review flow. The repository can prove that the submitted artifact is current;
it cannot approve, submit, or verify the Community listing on the maintainer's behalf.

After `pnpm check:figma-catalog` passes:

1. Open Figma Desktop and import or update the plugin from `packages/figma-plugin/manifest.json`.
2. Run the plugin and verify the Icons, Settings, and Info tabs, including the current package
   version and icon count.
3. If the UI changed, run `pnpm --filter @solar-icons/figma-plugin capture:community` and review the
   generated Community assets before uploading them.
4. Publish a new version from the Figma plugin management flow. If Figma exposes an optional
   release-notes field, it may contain the package version and logical icon count, but do not rely
   on it as a durable versioned changelog.
5. Complete any Figma review requested for the update, then verify the public Community listing
   and an installed copy of the plugin.
6. Mark `FIGMA-CATALOG-SYNC` complete in `.autonomos/TASKS.md` only after the Community update is
   actually published.

Do not add a runtime network request to avoid this manual step. Keeping `networkAccess.allowedDomains`
set to `none` preserves predictable offline behavior and makes the plugin's catalogue version
explicit and auditable.

Figma Community's publication flow may allow the maintainer to edit the global listing description,
but it does not provide a dependable, user-visible changelog for each plugin version. Update the
current icon count in that description when it changes, and keep the full package version, counts,
hash, publication date, and release notes in the repository commit and worklog.

## Release policy

- A package release that changes the static SVG map or metadata requires a plugin rebuild and a
  Figma Community update.
- A plugin UI or behavior change requires a plugin rebuild and a Figma Community update, even when
  the icon catalogue hash is unchanged.
- Documentation-only changes do not require a plugin update.
- The automated check is the release gate; the Figma Community submission is the manual completion
  step.
